# Services de traitement

`ExecutionContext` peut fournir de manière indépendante des primitives de moteur locales fiables, indépendamment des options des outils. Le traitement API continue de valider les artefacts d'entrée, d'appliquer les budgets et de vérifier les artefacts de sortie. Un service moteur retourne des relevés ou des pixels ; le gestionnaire de traitement public interprète ces relevés et construit le résultat. Les services sont limités à une seule exécution et ne modifient pas les moteurs CLI par défaut.

Les services facultatifs sont documentés dans `ExecutionContext` : lecture de symboles, OCR, reconnaissance vocale, masques de premier plan et rastérisation des PDF. Les enregistrements des pages PDF contiennent des données matricielles encodées et des dimensions physiques en points. L’encodage des données matricielles, l’assemblage des diapositives et le masquage irréversible restent dans les gestionnaires publics. Les enregistrements vocaux utilisent une langue et une liste de segments start/end/text. Les enregistrements OCR contiennent du texte ou les octets d’un PDF permettant la recherche textuelle pour chaque page, avec des dimensions physiques facultatives pour la remise à l’échelle.

Les modules de traitement JavaScript peuvent être utilisés indépendamment du pilote Python :

- `tools/developer/source_engine.mjs` exporte la transformation du code source et la gestion des résultats, une interface hôte pour un outil de formatage natif, des vérifications de l'arbre syntaxique, la validation locale de pointeurs JSON, la sélection de spécification API et le traitement de la recette de conteneur. Le chargement du moteur, l'isolation des processus et la durée de vie du parseur appartiennent à l'appelant.
- `tools/document_engine.mjs` exporte la conversion de documents sémantiques de base en utilisant un sous-ensemble des nœuds de documents Pandoc. Il accepte les services de parseur Markdown et HTML, omet le contenu actif et le chargement d’images externes, et écrit des LaTeX autonomes. Un service d’écriture PDF reçoit le document sémantique; la mise en page, les ressources de police et le rendu appartiennent à ce rédacteur. Les limites de complexité du parseur sont des paramètres fournis par l’appelant.

Le sous-ensemble du document couvre les paragraphes, titres, mise en évidence, code, liens, listes, citations et règles horizontales. Les tableaux sont représentés par des lignes de texte. Il ne prétend pas à la pleine fonctionnalité d'un moteur de composition de documents. La conversion de documents native CLI reste disponible avec ses contrats originaux de moteur.

Pour les installations sans exécutables de documents natifs, l’API Python de traitement accepte également `ExecutionContext(portable_documents=True)`. Markdown/HTML à PDF ou LaTeX utilise ensuite `tools/portable_documents.py` : analyse locale limitée HTML, MarkdownIt, LaTeX échappé et mise en page ReportLab avec ses polices Vera incluses. Il ne récupère jamais de ressources ni n’exécute de balisage source. Ce mode délibérément basique omet CSS et le contenu actif, représente les tableaux comme des lignes de texte, et rejette les glyphes PDF non pris en charge. `DocumentLimits` contrôle les nœuds, les imbrications, les blocs et les budgets de pages PDF indépendamment des limites d’octets d’entrée et de sortie. Installez les extras `documents` et `pdf`. La conversion Pandoc/TeX native reste par défaut ; les changements exclusifs à ces chemins natifs n’affectent pas le mode portable.

`tools/symbols.py` expose les paramètres du lecteur ZXing utilisés pour la lecture native. Les lecteurs fournis peuvent utiliser les mêmes formats, paramètres de rotation et d’inversion. Le gestionnaire de codes-barres normalise les alias de format avant d’assembler le résultat public. `input_image` et `pixel_input` partagent l’orientation de l’image et la composition du canal alpha sur fond blanc entre la lecture native et les lecteurs fournis basés sur les pixels. Les appelants peuvent réduire le budget de pixels indépendamment des paramètres de détection.

`tools/background.py` expose le checksum du modèle U2Net, `foreground_input` et `foreground_output`. L'entrée est un tenseur float32 en little-endian contigu avec la forme `[1,3,320,320]` ; la prédiction fournie est la première sortie float32 avec la forme `[1,1,320,320]`. L'inférence native et les prédictions fournies utilisent la même préparation de tenseur, la même normalisation du masque et le même redimensionnement de l'image. Les différences entre les environnements d’exécution de l’inférence peuvent encore affecter les résultats en virgule flottante.

`tools/transcription.py` expose `recognition_parameters`, y compris le modèle, la langue, le taux d’échantillonnage, la largeur du faisceau et le conditionnement du texte précédent. Un autre hôte d’inférence doit explicitement supporter ces paramètres ; des paramètres partagés n’établissent pas l’équivalence des implémentations de décodage ou des conversions de modèles quantifiés.

Le gestionnaire de développement utilise directement sqlparse et SQLFluff lorsqu'ils sont installés dans son environnement Python. Les commandes autonomes originales `sqlformat` et `sqlfluff` restent prises en charge lorsque ces imports ne sont pas disponibles. La validation SQL utilise le dialecte SQLFluff demandé, avec ANSI comme valeur par défaut ; elle n'exécute pas les requêtes.
